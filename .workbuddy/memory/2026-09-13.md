## 自动记账 Android App（首版交付）

在 `D:\Project\记账助手` 从零搭建了一个纯离线安卓记账 App，产出可安装的
`dist/AutoLedger-v1.0.0-release.apk`（4.8 MB，v2 签名，无 INTERNET 权限）。

### 技术选型（已定，后续沿用）

- Kotlin 2.0.21 + AGP 8.7.3 + Gradle 8.10 + JDK 17
- compileSdk 35 / targetSdk 35 / minSdk 26
- View + XML + Material 3，viewBinding；**不用 Compose**
- 存储用原生 SQLite（**刻意不用 Room**，避免 kapt/KSP 与 JDK 17 的注解处理器坑）
- 图表自绘（`ui/widget/DonutChartView`、`BarChartView`），零第三方图表依赖

### 自动记账的实现路径（关键结论）

非 root 设备读不到微信/支付宝的私有数据，所以走这三条路：

1. **NotificationListenerService** 监听 `com.tencent.mm` / `com.eg.android.AlipayGphone`
   的支付通知 → `PaymentParser` 抽金额+收支方向+商户 → `CaptureSink` 落库
2. 银行短信（可选，默认关）作为补充来源
3. **导入微信/支付宝官方导出的 CSV 账单**（最可靠的历史补录手段）

解析原则是「宁可漏，不可错」：金额与收支方向必须同时命中才记账，
`PaymentParser.NOISE_HINTS` 过滤验证码/营销类通知。

去重策略：`insert()` 默认以「金额 + 收支方向 + 时间窗口（默认 120~180s）」判重，
解决「支付通知 + 银行短信」同一笔钱记两条的问题。

### 自动分类

`CategoryEngine` 按关键词长度（priority）由长到短匹配，长词优先，
避免「饭」抢在「饭店」前命中。命中不了就落到「其他」并置 `auto_category=0`，
界面显示「待分类」徽标提示用户手动分类。规则存 `rule` 表，用户可增删。

## v1.0.1：真机两个 bug 的修复

真机反馈：① 明细里删掉的记录还在；② 连付几笔只记下第一笔。

### 根因（都是判重 / 生命周期问题，不是解析问题）

**② 漏记** —— `insert()` 的判重条件只有「金额 + 收支方向 + 时间窗（原 120s）」，
同一时段金额相同的后续几笔全被当成重复丢掉。测试时连付几笔同样金额，正好全中。
真机上还有一层：微信会把同一条付款通知反复改写，`StatusBarNotification.postTime`
每次改写都会往前走，之前一律拿 postTime 当交易时间，时间会漂。

**① 删了还在** —— 付款通知还挂在通知栏时，系统会重新投递一遍；
插入判重只查 `txn` 表，刚删掉的那条查不到，就被原样写回去了。
另外发现一个连带缺陷：`btnDelete` 在 `byId()` 返回前就可见，手快点了会因为
`editing == null` 静默返回（既没弹窗也没删）。

### 改法

- **判重拆三档**（`LedgerRepository.rejectReason`，顺序不能换）：
  ① 墓碑命中 → 丢弃；② 同来源：**20 秒**内且 `raw_text` 一字不差 → 重复；
  ③ 跨来源（通知 / 短信 / 账单）：金额 + 方向一致，窗口 **240 秒** → 重复。
  跨来源的窗口由 `insert(dedupWindowSec)` 传入，短信 300s、账单 300s。
- **墓碑表 `deleted_txn`**：`ledger.db` v1 → **v2**（`onUpgrade` 里 `createDeletedTable`）。
  删除时把 channel / direction / amount / raw_text / occurred_at 抄一份，
  30 分钟内拒绝同原文的重放。墓碑保留 3 天，`deleteAll()` 一并清空。
- **时间戳修正**（`PaymentNotificationListener.resolveOccurredAt`）：
  用一张 `LinkedHashMap(key -> (正文, 采用的时间, postTime))`（上限 64 条，LRU）判断：
  正文没变且 postTime 没往前走 = 系统重放，沿用上次时间（这样判重能精确命中原记录）；
  其余情况 = 新的一笔，用最新 postTime。
- **采集日志**（新增 `CaptureLog` + `LogActivity` + `activity_log.xml`）：
  每条通知的原文、识别结果、判重原因、授权连接/断开、删除命中行数、导入统计都留痕。
  存在 `filesDir/capture.log`，最多 300 行。入口在「我的 → 采集日志」。
  真机排查不用再连电脑抓 logcat。
- 删除按钮改为读完记录再显示，并把「实际命中几行」写进日志和 Toast。

### 验证方式

- 用 Python 的 `sqlite3` 复刻了三档判重的 SQL，跑 7 个场景全通过
  （同金额连付 3 笔都记上、重放被挡、跨来源去重、删除后 2/25 分钟重放被挡、40 分钟后放行、
  金额不同不入重、收支方向不同不入重）。脚本是一次性验证，没入库。
- `assembleRelease` 通过；`apksigner` 验签指纹与 v1.0.0 完全一致
  （SHA-256 `bf0e168e…71e6e99`，可覆盖安装）；`aapt2 dump badging` 确认
  `versionCode=2 / versionName=1.0.1`，权限表里仍然**没有 INTERNET**。
- 产物：`dist/AutoLedger-v1.0.1-release.apk`（旧 v1.0.0 已删除）。

### 遗留 / 待观察

- 墓碑窗口（30 分钟）+「原文一字不差」的取舍：极端情况下，
  删掉一笔后 30 分钟内又发生**完全一样**的一笔，会被静默挡掉。
  日志里有记录，可手动补。
- 真机仍需实测：微信同一条通知连改几次时的落库条数与时间是否正常。
- 支付宝部分场景通知不带商户名，仍需靠 CSV 导入补齐。

### ⚠ 关键坑：中文项目路径会让 Gradle test worker 加载不到测试类

`D:\Project\记账助手` 含中文时，`:app:testDebugUnitTest` 会**全部报
`ClassNotFoundException: com.local.autoledger.XxxTest`**。但类文件本身是好的
（`javap` 能读、原生 `java -cp ... JUnitCore` 也能跑通）。结论是 Gradle test worker
在中文路径上翻车，不是我们的代码问题。

**修法（已在根 `build.gradle.kts` 落地，不要删）**：把 build 目录整体挪到纯 ASCII 路径
`D:\Project\AutoLedger-build`，源码路径不动。路径本身就是 ASCII 时会自动退化回默认。

排查手法留档：建一个 junction（`D:\proj_ascii_test` → 项目目录）跑同一任务就能复现/验证。

### 第二层：模拟器端到端（跑真 APK）

- Android SDK 里补装 `emulator` + `system-images;android-35;google_apis;x86_64`（约 4.6 GB，**在 D 盘**）
- AVD 名 `ledger_test`（pixel_6 / API 35 / x86_64）

**核心难点：通知来源包名伪造不了。** `NotificationListenerService` 拿到的
`StatusBarNotification.packageName` 由系统按安装包认定，应用改不了。要让 AutoLedger
看到 `pkg == com.tencent.mm` 的通知，只能真的装一个叫这个名字的 App 上去。

于是新增 `:paysim` 模块（纯 framework，无任何依赖），两个 flavor 产两个「马甲」：
`wechat` → `com.tencent.mm`，`alipay` → `com.eg.android.AlipayGphone`。
`SimReceiver` 收 adb 广播后 `notify()` 一条假支付通知。
**文案走 Base64 传**（`--es text64 <b64>`）：adb shell 在 Windows 控制台传中文极易乱码，
乱码会直接改变解析结果，那测的就不是真实逻辑了。

驱动脚本：`tools/emulator-e2e.ps1` + `tools/ledger_assert.py`（用 Python 的 sqlite3
读 `run-as` 拉回来的库做断言）。脚本流程：构建 → 起模拟器 → 装三个 APK →
`cmd notification allow_listener` → 投假通知 → 拉库断言 → uiautomator 驱动删记录 → 截图存 `dist/emulator-e2e/`。

### ⚠ 坑：Windows PowerShell 5.1 读 .ps1 不看 BOM 就是 GBK

给脚本写中文注释/输出时，**必须存成带 UTF-8 BOM 的 .ps1**，否则 PS 5.1 按 GBK 解释，
中文变 `鎸囧畾`，字符串引号被撑破，报一堆莫名其妙的「意外的标记 }」。
加 BOM：`[System.IO.File]::WriteAllBytes($p, [byte[]](0xEF,0xBB,0xBF) + [System.IO.File]::ReadAllBytes($p))`。

### C 盘空间事故复盘（重要，别重演）

用户反馈 C 盘少了十来个 G。真实账：

- **模拟器把 C 盘吃掉了约 9.7 GB**：AVD 默认建在 `~/.android/avd`；更坑的是
  关模拟器时会把整个 data 分区写成 `userdata-qemu.img`（**6 GB**），
  再加 `snapshots/default_boot/ram.img`（2.56 GB）。
- 一个中间态假象：跑起来时量 AVD 目录只有 2.8 GB，**6 GB 的 userdata 是关机那一刻才写出来的**，
  所以「量一次」会严重低估。
- **删除会进回收站**（本机 safe-delete 机制），所以 `Remove-Item` 后 C 盘可用空间不涨 ——
  文件还在 `C:\$Recycle.Bin`，得再永久删一次才算真释放。

**已处置**：
- 用户级环境变量 `ANDROID_AVD_HOME = D:\develop\android-avd`，AVD 重建到 D 盘
- `config.ini` 关掉快照（`fastboot.forceColdBoot=yes` / `firstboot.saveToLocalSnapshot=no`），
  `disk.dataPartition.size=3072M`、`hw.ramSize=2048M`，免得再膨胀
- 精确定位回收站里那 104 个 AVD 条目并永久删除（**只删自己的，用户自己的 359 MB 一律不碰**）
- 结果：C 盘可用 38.3 GB → **54.2 GB**

顺带查明：`C:\pagefile.sys` 被撑到过 21.8 GB（跑模拟器 + 8 个 Gradle 守护进程时），
这部分要重启或手动设固定大小才会还回来。另外 `%TEMP%` 里约 2.2 GB 是
Docker Desktop / WorkBuddy / VS Code 的更新器残留，**不是本项目产生的**。

### 环境怪癖（补充）

- `%TEMP%` 里的日志文件是 PowerShell 工具 stdout 被吞时的唯一可靠出口
- 全盘 `Get-ChildItem C:\ -Recurse` 会被沙箱拦（它会去读 `~/.ssh`），别做全盘扫描

## 模拟器端到端首次跑通（当晚）

前 6 步全部通过：构建 → 起模拟器 → 装三个 APK → 开通知使用权 → 投 5 笔假支付 → 判重。
截图与库快照在 `dist/emulator-e2e/`。

实测结果：

| 投递的通知 | 落库结果 |
|---|---|
| 微信 向 星巴克 付款 28.00 元 | 支出 · 餐饮 |
| 微信 向 全家便利店 付款 9.50 元 | 支出 · 日用百货 |
| 微信 向 滴滴出行 付款 36.80 元 | 支出 · 交通 |
| 支付宝 支付成功 25.00元 | 支出 · 其他（无商户名 ⇒ 待分类 auto_category=0）|
| 支付宝 收款成功 88.00元 | **收入** · 其他收入 |
| 同一条 19.90 元通知连投 3 次 | 只记 1 笔，另两次日志写「同一条通知重复投递（20s 内）」|

界面上「本月支出 139.10 / 收入 88.00 / 结余 -51.10」与库里的行对得上。

### 这一跑直接查出 2 个真代码问题（已修）

1. **`raw_text` 存成了三份**：`EXTRA_TEXT` 与 `EXTRA_BIG_TEXT` 内容相同（BigTextStyle 本来就这样），
   `PaymentNotificationListener` 把它们直接 join 了。加 `.distinct()`。
2. 系统偶尔投递正文为空的通知更新，会往采集日志灌一条无意义的「未识别」。正文为空时直接 return。

### harness 自身踩的坑（已修，别再犯）

- `adb pull` 把进度写到 **stderr**，`$ErrorActionPreference='Stop'` 下会被当成致命错误、脚本当场中断
  → 调用原生程序期间必须临时降级成 `Continue`
- 用 `& $Py` 直接吃 Python 的 stdout 会被控制台编码（GBK）拆坏 UTF-8，
  **连 JSON 的引号都能吃掉** → 改成 Python 写文件（`--out`）+ `Get-Content -Encoding UTF8`
- `Get-Command python` 会先命中 WindowsApps 下的**应用商店占位程序**（不是真解释器）
  → 候选必须真跑一次 `import sqlite3` 才算数
- **`pm clear` 会把通知使用权一起清掉**，且 `settings get` 读到新值有延迟
  → `allow_listener` 之后要轮询等
- **`am start` 拉不起 `exported=false` 的 `EditTransactionActivity`**
  → 删除场景改成走真实路径：在明细里点那一行进编辑页
- 系统权限框（`permissioncontroller`）会盖在界面上，uiautomator 只能 dump 到对话框本身
  → 每次操作界面前先 `Dismiss-SystemDialog`
- 拉设备上的二进制别用 `cmd /c "... > file"`（会过文本编码，还被沙箱卡）
  → `Start-Process -RedirectStandardOutput` 或 `adb shell screencap` + `adb pull`
